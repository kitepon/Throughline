# ADR 0069: Windowsの後継は製品所有の端末で直接起動する

- 日付: 2026-10-17
- 状態: 採用
- 関連: [ADR 0068](0068-claude-waits-before-stopping-source.md)

## 問題

Windowsでは共有のClaude背景サービスが再起動し、異なる権限のプロセスがサービスの札を
持つと、元の通常権限の会話から接続できなくなる。共有サービスを一度入れ替えただけでは
再発を防げない。0.16.37で実受入後に再発した。

## 方針

Windowsの自動継続は共有サービスを操作せず、製品が所有する非表示のConPTYで通常の
Claude対話セッションを直接起動する。Windows用のoptional dependencyとしてnode-ptyを使い（Unixの導入をnative build必須へ変えない）、利用者の画面を開いたり切り替えたり
しない。native実行ファイルまたはnpmのPowerShell shimを使い、batchだけのshimは端末を作る前に拒否して旧い道具を通す。同じproject・モデル・effort・権限とRemote Controlを維持する。後継IDは起動前に
決め、実UserPromptSubmitによる記憶受領後にだけ旧い道具を終了させる。

端末の所有者は引き継ぎworkerであり、後継が存在する間は端末を維持する。workerの作業ディレクトリは製品状態の下とし、導入先を更新不能にしない。端末の終了を記録した後、専用workerも終了してnative addonのスレッドを残さない。起動失敗では
所有する後継の終了を確認してから旧い作業を通す。失敗の確定とworkerの最初の結果を同じ処理で行い、再開した旧い会話へ古いworkerが後から書き戻さない。結果不明を成功扱いせず、重複起動は
行わない。既存の共有daemon・他のworker・利用者の会話を停止しない。

Linux/macOSの既存起動と4ハーネスの配線は維持する。Windowsの受入は共有サービスの
到達性に左右されないこと、受領・実道具・Stop保存・Remote Control接続先の登録を
確認する。これは方針であり、実装・配布・現地受入が終わるまで完了とは扱わない。

## 受入の根拠

2026-10-17、Windowsの通常権限・セッション1で候補版を通した。共有daemonが別の権限で
動いている状態を変えず、後継は実UserPromptSubmitを4.7秒で受領し、起動元のプロセスが
終了した後も同じ後継がRead→Writeを実行した。入力に含めないnonceの内容一致、L2/L3の
実Stop保存、同じ後継のRemote Control登録を照合した。モデルは受入専用Haiku、権限は
今回の障害元と同じbypassPermissionsを試験用セッションだけに指定した。

先行するauto権限の試験は受領・Read・Remote Control登録まで進み、Writeの許可待ちに
なった。許可を自動承認したり、利用者設定を変えて成功にしていない。試験だけを停止し、
上記の権限継承の試験と区別した。別HOME・偽CLIが77で終了する負の試験では、最初の
道具が2.4秒で通り、実際の終了と失敗を保持し、DBを作らなかった。

これは当該候補の実機受入であり、配布物の照合・導入・導入後の受入は公開工程で別に行う。
