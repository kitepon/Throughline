# ADR 0072: 準備失敗後に継続する本人の会話を配送先として保つ

日付: 2026-10-22

## Context

macOSの旧版0.16.38が子作業の終了前に親を停止し、引き継ぎが失敗した。
親の会話を復旧して作業と連絡を再開しても、公開`successor`は古い失敗を
`pending`として返し続け、外部consumerが新しい配送を拒否する状態が残った。
停止前の準備を行う0.16.39以降でも、停止未許可の準備失敗が同じ形で返る。
また、native状態の確認から要約の完了までに子作業が始まる可能性がある。

## Decision

- 0.16.43では実際のPreCompact CLIの例外境界にも同じ保護を適用する。要求のID照合・
  transcriptの読取等が例外になっただけで停止を許可しない。元IDが有効で、読取専用の
  状態確認により実行中要求・既知の後継・配送・結果不明の作用が無いと確認できた時は、
  警告を返して元の会話を継続する。初回DB不在は新規作成せず確認する。
  有効な元IDを特定できない、DBを読めない、既存の作用・所有がある場合は保護を維持し、
  担当へ保存済み状態の照合を求める。失敗を「圧縮だけ停止」と呼ばず、元作業の停止と明示する。
  この例外経路もID/種類/絶対pathかどうかだけを診断へ記録し、会話本文は記録しない。

- native状態は要約の前と後に確認する。停止許可の直前にも元turn・未完了操作・
  native状態を照合し、子未完了なら`continue=true`で同じ本人の会話を継続する。
  ゴール停止、後継作成、画面切替、配送は行わない。停止後・配送前の再確認も維持する。
- `successor`の`pending`は失敗履歴の一覧ではなく、現在の引き継ぎ待ちを返す。
  `failed`で、後継ID・試行中mutation・受付ID・開始turnが無い要求に限り、
  停止許可が明示的にfalse、または元turn以後にモデルの発言・道具・完了等の
  実作業を元記録で確認した場合は除外する。入力を受けただけでは除外しない。
- `unknown`、作成・注入の結果不明、既知の後継、元記録の読取不能は保持する。
  最新の安全な失敗によって、より古い未解決の作用を隠さない。履歴DBは変更しない。
- JSON schema `throughline.codex_auto_handoff_successor.v1`とfield構造は維持する。
  `pending=null`の時は既存の`current_thread_id`で連絡できる。古い失敗は`status`で確認する。
- 警告は本人の元会話のURLを返す。復旧画面も本人の会話を入口とし、子・workerを
  利用者の会話相手に置き換えない。停止未許可・元前進・作用不明に再試行を勧めない。

## Limits and validation

- 公開CLIをsubprocessで起動し、実際のthread照合失敗が`continue=true`になることと、
  不明な作成・実行中要求・既存後継・配送済み状態が`continue=false`で保護されることを検証する。

- OSのURL受付や設定一致は、画面表示・入力可能の証拠ではない。機械状態の
  `continued`と、利用者が本人の会話を見て話せる受入を区別する。
- 別processで動くhostとの照合は原子的ではない。停止前の再照合だけを根拠に
  停止後・配送前の境界照合を省略しない。
- request→worker→successor試験は子未完了時の停止未許可・作用0件を検証する。
  準備中の子開始、元の実作業再開、入力だけのturn、読取不能、結果不明、
  既存後継と複数の失敗履歴、および復旧画面の案内を回帰試験に含める。
- 既存の失敗要求のresume、本文再送、実作業の子停止を本修理の適用条件にしない。
