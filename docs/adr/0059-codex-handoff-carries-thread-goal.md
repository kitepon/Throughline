# ADR 0059: Codex の旧タスクのゴールは、引き継ぎの初めに止めて、後継へ運ぶ

日付: 2026-10-13

## Context

Codex には、タスクごとのゴール（`/goal`）がある。目標の文を決めておくと、タスクが手すきになるたびに Codex が自分で
次のターンを起こし、目標が終わるまで続ける。

2026-10-13、Windows の Codex Desktop（同梱の Codex 0.162.0-alpha.17.2、Throughline 0.16.27）で、自動継続が
引き継いだ後の旧タスクが止まらなかった。

- 22:04:09 に旧タスクを止めて引き継ぎを始め、22:05:44 に後継が作業を続けた（`continued`）。引き継ぎ自体は成功している。
- 旧タスクには、20:10 に利用者が付けたゴールが「実行中」のまま残っていた。後継にはゴールが無かった。
- 旧タスクでは、22:04:10 から 1〜2 秒おきに新しいターンが始まり続けた。23:43:35 までに 2,067 回。
  どのターンも入力は Codex 自身の文脈（`<codex_internal_context source="goal">` で始まる続行の指示）だけで、人の入力は 0。
- ターンが始まるたびに、文脈が上限を超えているので `PreCompact(auto)` が来る。Throughline は「引き継ぎ済みの旧タスクへ
  新しい入力が来た」（ADR 0039）として、ターンを止め、後継を画面に開いた。
- 利用者には、「タスク終了」の通知が続き、画面が後継へ切り替わり続ける様に見えた。旧タスクの記録（rollout）は
  約34MB まで増えた。モデルは呼ばれていない（止めるのはモデルを呼ぶ前）。
- 引き継ぎの最中（22:04:10〜22:05:44）にも同じターンが来ていた。こちらは「引き継ぎの最中の入力」（ADR 0040）として
  止まっていた。

原因は、Throughline がゴールを扱っていなかった事にある。

- Codex は、タスクが手すきになるたびに DB のゴールを読み、`active` なら続行の指示でターンを始める
  （`codex-rs/ext/goal/src/extension.rs` の `on_thread_idle` → `runtime.rs` の `continue_if_idle`）。
  hook が止めたターン（`turn_aborted`、`interrupted`）の後も同じ。利用者が自分で中断した時だけの持ち越しの印は、hook の止めでは付かない。
- 後継は新しいタスクなので、ゴールを持たない。後継は継続の指示の1ターンを終えると、そこで止まる。
  ゴールで動かしていた作業が、引き継ぎを境に自分では続かなくなっていた。

Codex の app-server には、ゴールを読む・変える・消す口がある（`thread/goal/get`・`thread/goal/set`・`thread/goal/clear`。
experimental）。別の process から使える。確かめた事（Linux の Codex 0.162.1 と、Windows の実機）:

- 別の process が `status: 'paused'` を書くと、タスクを開いている process は次の手すきで続行を起こさない
  （Windows の実機で、連続が1ターンの内に止まった）。
- ゴールの無いタスクへ、別の process が目標の文つきで `status: 'active'` を書ける。そのタスクがターンを動かしている間に
  書くと、タスクを開いている process は、そのターンの後から続行を起こす。
- 手すきのタスクへ `active` を書いても、その場では続行が起きない。次にそのタスクのターンが終わった時から起きる。
- `status: 'paused'` と目標の文を一緒に渡して、止まった状態のゴールを新しく作れる。

## Decision

1. worker は、引き継ぎの最初に、旧タスクのゴールを読む。`active` なら `paused` にする（`pauseAutoHandoffSourceGoal`）。
   ゴールは消さない。止めたかどうかを、引き継ぎの記録（`runtime_json.goalCarry.paused`）へ書く。目標の文は記録へ写さない。
2. 後継が作業を続けたのを確かめた後（`continued` の直後、順番待ちを運ぶより先）に、旧タスクのゴールを後継へ運ぶ
   （`carryAutoHandoffGoal`）。後継の最初のターン（継続の指示）が動いている間に付けるので、そのターンの後から Codex が続ける。
   - 目標の文はそのまま写す。予算（`tokenBudget`）があれば、旧タスクで使った分を引いた残りを渡す。
   - この製品が止めたゴールは、後継では `active` にする。利用者が止めていたゴール（`paused`）は、`paused` のまま運ぶ。
   - 完了したゴール（`complete`）と、Codex が上限や行き詰まりで止めたゴール（`budgetLimited`・`usageLimited`・`blocked`）は運ばない。
   - 後継にもうゴールがあれば、書き換えない。
   - 運ぶ時に旧タスクのゴールが `active` なら（最初の一時停止が効かなかった）、先に `paused` にしてから運ぶ。
3. 旧タスクのゴールは `paused` のまま残す。旧タスクは引き継ぎ済みなので、そのゴールは動かない。
4. ゴールを読めない・書けない時も、引き継ぎは止めない（ゴールの口が無い版の Codex を含む）。理由は worker のログに残す。
5. 途中で止まった引き継ぎ（`failed`・`unknown`）では、ゴールを後継へ運ばず、旧タスクのゴールも `active` へ戻さない。
   戻すと、止まったままの旧タスクで、続行のターンと引き継ぎの失敗が繰り返される。失敗の画面に、ゴールを止めてある事と、
   旧タスクで続ける時の戻し方を書く。やり直しで `continued` になった時に運ぶ。同じ旧タスクから新しい引き継ぎを作った時は、
   前の引き継ぎが止めていた事を引き継ぐ（後継では `active` にする）。
6. 引き継ぎ済みの旧タスクへターンが来た時（ADR 0039 の道）に、次の2つを足す。
   - そのターンの入力が Codex 自身の文脈だけなら（`<codex_internal_context` で始まる物だけ）、後継を画面に開かない。
     人が入力していないのに画面を切り替えない。ターンを止めて後継を示す事は変えない。
   - 旧タスクにゴールが動いたまま残っていないかを、別の process で確かめる（`auto-handoff settle-goal`。hook は待たない）。
     動いていれば `paused` にし、今の一番先の後継にゴールが無ければ `active` で運ぶ。同じ旧タスクへは30秒に1回まで。
     0.16.27 までの版が引き継いだ旧タスクと、引き継いだ後で利用者が旧タスクのゴールを再開した時が当たる。
     片付けた事は `~/.throughline/codex-auto-handoff/goal-settles.jsonl` へ1行残す（時刻・ID・付けた状態。目標の文は書かない）。

## Consequences

- ゴールで動かしていたタスクは、引き継いだ後も後継がゴールで続ける。旧タスクは止まる。
- 引き継ぎの最中に来る続行のターンは、worker がゴールを止めるまでの数秒の分だけになる。
- 後継のゴールの使用量（`tokensUsed`・`timeUsedSeconds`）は 0 から数え直しになる。予算は残りを渡すので、合計の上限は変わらない。
- 6 の片付けで運んだゴールは、後継が手すきの時は、その場では動き出さない。後継の次のターンが終わった時から Codex が続ける。
- 旧タスクの画面のゴールの表示は、別の process が書いた変更なので、Codex Desktop がそのタスクを読み直すまで古いまま見える事がある。
- `continued` を記録した直後に worker が落ちると、ゴールは旧タスクで止まったまま、後継へは運ばれない。旧タスクは動かないので
  連続は起きない。利用者が後継でゴールを付け直す必要がある。
- `blocked` などで止まっているゴールは運ばない。旧タスクに残る。
- 引き継ぎ1回につき、Codex の app-server への接続が2回増える（最初の読み書きと、運ぶ時）。
- Claude Code の自動継続は変えない。Claude Code にはタスクごとのゴールが無い。

## 確かめた範囲

| | macOS | Linux | Windows |
|---|---|---|---|
| Codex Desktop | 直した版の関数（止める・運ぶ・片付ける）を、Desktop 同梱の Codex（0.162.0-alpha.17.2）へ通した（25項目） | 同じ確認を codex-cli 0.162.1 で。本物の Codex Desktop（同梱の 0.162.0-alpha.2）で、ゴールを持つタスクの引き継ぎを8回続けて通した | 起きた端末。旧タスクのゴールを `paused` にして、連続が止まるのを見た。関数の確認（25項目）を Desktop 同梱の Codex（0.162.0-alpha.17.2）で。起きた旧タスクの本物の記録へ、直した版の hook の入口を読むだけで当てた |
| Claude Code | 変更なし（ゴールが無い） | 同じ | 同じ |
| Grok | 変更なし（自動継続が無い） | 同じ | 同じ |
| Cursor | 変更なし（自動継続が無い） | 同じ | 同じ |

Linux の通し（2026-10-14 00:05〜00:14 JST）で見た事:

- タスクを Codex Desktop で開くと、実行中のゴールを持つタスクは、入力を待たずに続行のターンを始めた。
- 引き継ぎのたびに、止めたターンの直後から続行のターンが 0.15 秒ほどの間隔で来た。worker がゴールを止めるまでの1秒以内に 4〜5 回で、
  その後は来ていない。8回とも `goalCarry` は `{"paused":true,"carried":"active"}`。
- 最後の後継が作業を終えるとゴールは完了になり、Codex Desktop の画面の側が `thread/goal/clear` を送ってゴールを消した。

macOS と Windows の本物の Codex Desktop の画面で、ゴールを持つタスクが引き継がれる通しは、公開の時点では確かめていない。
