# ADR 0056: Grok が書き直した chat_history は、保存済みのターンと本文で見分け、世代ごとに番号を分ける

- Status: Accepted
- Date: 2026-10-12

## Context

Throughline は、会話の記録（transcript）の中の位置を `turn_number` にして、発言を bodies へ保存する
（`backfillBodies`）。記録を読むたびに全部の群を見て、群の断片の位置が bodies にあれば「保存済み」として飛ばす。
Claude Code と Codex の記録は追記だけなので、位置は変わらない。

Grok は、文脈がいっぱいになると会話を自動圧縮し、`chat_history.jsonl` を書き直す。書き直した後のファイルは、
要約の行（`synthetic_reason: "compaction_meta"`）、印の無い user 行1つ、続きの指示（`compaction_meta`）、
注意書き（`system_reminder`）、圧縮をまたいだターンの assistant の行、の並びになる。会話の置き場には
`compaction/segment_NNN.md` と `compaction_checkpoints/` が出来る。位置は 0 から振り直しになる。

2026-10-12 に BellTeam コンテナ（Linux、0.16.5、Grok 1.0.46）で、Stop が
`completed pair was not captured before receipt publication` で2回失敗した（Grok は Stop の hook を2本起こす）。

- 会話は毎朝の予定で動く Grok の席。bodies には 6 ターン（位置 8・13・19・23・30・36）が保存済みだった。
- 08:17:41 に Grok が自動圧縮した（`compaction/` の時刻）。ファイルは 105 行、群は 6 → 1 になった。
- 08:24:04 の Stop で、その1群の断片は位置 5〜9。位置 8 が保存済みの番号と重なり、群ごと「保存済み」として飛ばした。
  代表の断片は位置 9 で、bodies に無い。完了受領を書く所で、対の行が見つからず失敗した。
- 圧縮をまたいだターンの依頼と回答は、Throughline の記憶に入らなかった。この会話の後の Stop も、同じ群で毎回失敗する。

同じコンテナの別の Grok の会話（2026-09-30、圧縮3回）では、代表の位置が保存済みの番号と重なっていた。この形は
失敗が出ず、古いターンの受領が出し直されるだけで、圧縮をまたいだターンは黙って落ちていた。その後のターンは、
古い番号の間に入って保存されていた（位置 14 の後に 12）。

コンテナの Grok の記録 101 件のうち、圧縮の跡があるのはこの2件。最新の 0.16.25 でも同じ（合成した記録で再現）。

もう1つ、Grok が自分で書く user 行の扱いがあった。`system_reminder` の行は、Throughline が user の発言として
読んでいた。記録の中の 238 行の前後を種類だけで数えると、依頼（`prompt_index` を持つ行）の直後が 23、道具の結果の
後で assistant の行が続く（ターンの途中）のが 37、依頼の前が 165、残りの 13 は圧縮の直後（4）と、後ろに何も無い行（9）
だった。依頼の直後に来ると、そのターンの user の本文が注意書きになる。ターンの途中に来ると、1つのターンが2つの群に
割れる。終わったターンの後に注意書きだけが来て、依頼なしで次のターンが始まる形は、1つも無かった。

## Decision

1. **Grok が自分で書いた user 行は、ターンの始まりにも本文にもしない。** 対象は `synthetic_reason` が
   `compaction_meta` と `system_reminder` の行（`message` を持たない Grok の形の行だけ）。位置は進める。
   Claude Code の圧縮の要約行（ADR 0032）と同じ扱い。`task_completed` は host が自分から始めるターンなので、
   今までどおりターンの始まりにする。知らない印の行も今までどおり。
2. **書き直される記録では、保存済みかを本文でも確かめる。** host の adapter に `rewritesTranscript` を足し、
   Grok だけ true にする。true の host では、群の断片と同じ位置に、同じ本文の assistant 行がある時だけ「保存済み」とする。
3. **書き直しの後のターンは、世代を分けた番号で保存する。** 世代 g のターンは
   `g × 1,000,000 + 記録の中の位置`。世代 0 は今までの番号と同じ。今の世代は、保存済みの番号の最大から読む
   （`floor(turn_number / 1,000,000)`）。別の表や置き場は持たない。
4. **書き直されたかは、今の世代の保存済みの行で決める。** 今の世代で保存した assistant 行のうち、記録の同じ位置に
   同じ本文が無い行が1つでもあれば、書き直されたとして次の世代へ進む。保存していない群は、新しい世代の番号で入れる。
   古い世代の行と本文が合う群（巻き戻しで残った前半など）は、保存済みとして飛ばす。
5. **完了受領は、行が実際にある番号で出す。** 保存済みの群は、合った行の番号を返す。合成行の扱いが変わる前に
   2つの群として保存されていたターンは、後ろの行の番号で出す。
6. Claude Code・Codex・Cursor は今までどおり、位置だけで決める。

## Consequences

- Grok の自動圧縮をまたいだターンが保存され、受領も出る。その会話の後の Stop も失敗しない。
- すでに番号が重なっている会話（上の2件）は、この版の最初の Stop で、落ちていたターンが世代 1 の番号で入る。
  圧縮の後に古い番号の間へ入っていたターンは、そのままの番号で残る（並びは直さない）。
- 圧縮をまたいだターンの user の本文は、圧縮の後に残った印の無い user 行になる（始まり方は `unknown`）。元の依頼の
  文が `chat_history.jsonl` に残っているかは、確かめていない。
- 巻き戻しで消されたターンは、bodies に残る。起きた会話として記憶に残す。
- `turn_number` は 1,000,000 以上になる事がある。番号を記録の位置として使う処理は、Grok には無い（L3 の抽出と
  flush barrier は Claude Code の記録の形だけを読む）。1つの記録に 1,000,000 行以上の本文がある事は想定しない。
- 保存済みかの判定が assistant の本文の一致に頼る。Grok の assistant の本文の取り出し方を変える時は、保存済みの
  行と合わなくなって、全部の群が次の世代へ重ねて入る。変える時は、この判定も一緒に見直す。
- 同じ位置に同じ本文の行が、書き直しの前後でたまたま並ぶと、後の方を保存済みと見て落とす。位置と本文の両方が
  合う必要があるので、起きにくい。

## 確かめた事・確かめていない事

- 確かめた: 単体試験（圧縮の2つの形、2回目の圧縮、巻き戻し、合成行を user として保存していた頃の行との両立、
  追記だけの host は不変）。本物の hook の命令（`process-turn`）へ、合成した記録を通した（切り離した HOME）。
  コンテナの本物の DB の Grok の会話 110 件を、メモリへ写して空実行した（書き直しと判定したのは圧縮の跡がある2件だけ、
  2回目の実行で増えない）。
- 確かめていない: 本物の Grok が圧縮をまたぐ場面での、この版の動き（狙って起こせるかを確かめていない）。
  Grok の巻き戻しが `chat_history.jsonl` をどう書き直すか（実物を見ていない。試験の形は想定）。
  Cursor が記録を書き直すか（コンテナの取り込みの記録 169 会話に、群が減った跡は無い）。
